按目标管理依赖

一个清晰的 Qt 项目从 target 开始：

每个模块都通过 find_package 的 COMPONENTS 声明，并链接对应的导入目标。PRIVATE 表示依赖用于构建此目标；若公开头文件暴露 Qt 类型的库需要被其他目标使用，再考虑 PUBLIC。避免全局 include_directories() 和手工拼 .lib/.so 路径，以免 Debug/Release 或平台路径串错。

Debug 和 Release

Debug 构建便于断点调试、检查变量和定位问题；Release 构建用于优化和交付。单配置生成器（常见 Ninja/Unix Makefiles）可以用 CMAKE_BUILD_TYPE：

Visual Studio、Xcode 等多配置生成器则通常在构建时指定 --config Debug 或 --config Release。不要把 CMAKE_BUILD_TYPE 当成所有生成器通用的配置选择方式。

缓存、生成器和 Qt 路径

CMake 首次配置会在构建目录写入编译器、生成器和依赖路径。切换 Qt 安装目录、编译器、架构或生成器时，建议新建干净构建目录重新配置；同一构建目录里换 Kit 往往留下错误缓存。可以用 cmake -S . -B build -LAH 查看缓存变量。

Qt Creator Kit 会为 Qt Creator 项目传入合适的 Qt 路径和编译器。命令行项目可使用安装目录下的 qt-cmake，或设置 CMAKE_PREFIX_PATH 指向对应 Qt 套件。不要把多个 Qt 主版本路径同时加入系统全局 PATH，以免运行时误加载另一套 DLL/共享库。

第三方库和可复现构建

对 Qt 自带的模块明确写入 find_package(Qt6 ...)。第三方依赖优先使用项目统一的包管理或 CMake config package，并记录版本约束。团队统一 Qt、编译器、CMake/Ninja 版本及构建配置；CI 应从干净构建目录配置，以发现本机偶然遗留的依赖。

构建失败时先看第一条真正的 compiler/linker error，而非后续级联错误。找不到头文件通常是模块未链接；undefined reference 常是漏链接模块或函数定义；moc 相关错误通常要检查 Q_OBJECT、头文件是否纳入目标以及自动 moc 配置。

编译性能经验

保持增量构建目录，避免每次全量清理；把大型项目拆为合理的库目标；让头文件只包含必需依赖，能用前置声明时减少 include；为重型任务使用 Ninja 和并行构建。不要为了加快编译而隐藏警告或关闭 moc 检查。先测量瓶颈再优化。

Qt 的构建与部署命令说明见 Getting started with CMake 和 Qt CMake 手册。
