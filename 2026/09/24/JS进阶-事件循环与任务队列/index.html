JavaScript 进阶：事件循环、微任务与宏任务

发表于2026-09-24|更新于2026-09-24|JavaScript进阶
|字数总计:664|阅读时长:2分钟|阅读量:

单线程不等于所有事情都同步

在常见浏览器主线程中，JavaScript 一次只执行一段脚本。调用函数会把执行压入调用栈；函数返回后弹出。计时器、网络请求等由宿主环境处理，完成后把回调排入相应队列，等待主线程有机会执行。

可以粗略理解为：执行当前脚本任务，清空微任务队列，然后宿主有机会进行渲染，再取下一个任务。细节由宿主环境和规范定义，不能把简化模型当成所有运行时完全相同的实现。

Promise 回调为什么先于 timer

输出顺序是 A、B、promise、timer。同步代码先跑完；then 回调进入微任务队列；计时器回调进入后续任务队列。setTimeout(..., 0) 不是立刻执行，只表示计时器到期后可以排队。

微任务会在检查点执行

输出是 1, 3, 2, 4。最初队列里有两个 Promise 回调。执行第一个时追加的微任务排在已有的 3 后面。微任务通常会一直清空到队列为空，因此不停递归安排微任务可能让页面长时间得不到渲染机会。

浏览器与 Node.js 的差异

浏览器和 Node.js 都有事件循环，但阶段与 API 不完全相同。Node.js 还提供 process.nextTick，它有自己的调度语义；不要把浏览器的队列示意图直接套用到 Node.js 的所有边界情况。跨运行时教程应聚焦标准 Promise 和明确列出的宿主 API。

分析执行顺序

  1. 标出同步代码和每个回调注册的位置。
  2. 识别宿主环境：浏览器还是 Node.js，涉及哪些 API。
  3. 分别记录同步执行、微任务和计时器/事件回调。
  4. 按队列顺序模拟，每执行一个回调就记录它新添加的任务。
  5. 对渲染时机等问题，记住浏览器可以在适合的检查点渲染，但不保证每个任务后立刻重绘。

长时间同步循环会占用主线程，事件和交互都无法及时响应。可把大任务分块，在不同任务之间让出执行机会，或将纯计算转到 Web Worker。微任务适合承接短小的后续工作，不适合无限分片。
