Qt 进阶（十）：跨平台部署与打包经验

先区分构建和部署

开发机上程序能运行，不代表发给别人也能运行。开发环境通常通过 IDE 环境变量找到 Qt 库和插件；交付包需要包含运行所需的 Qt 库、平台插件、图像格式插件、资源和第三方依赖。部署包必须在干净机器或干净虚拟机上验证。

Qt 6 的 CMake 部署 API 可以生成部署脚本，再在安装阶段收集运行依赖。Widgets 项目可按此思路设置：

使用 qt_standard_project_setup() 时会引入 GNUInstallDirs，可使用 CMAKE_INSTALL_BINDIR。配置 Release 后运行 cmake --install build --prefix staging（单配置构建目录按实际路径替换），检查 staging 中是否有可运行程序及其依赖。Qt Quick 应用需使用对应的 QML 部署脚本，并确保 QML 模块纳入部署。

Windows

在与应用相同 Qt 套件的环境中构建 Release，再对可执行文件运行该套件的 windeployqt：

它会复制常用 Qt DLL 和所需插件。检查 platforms\qwindows.dll 等插件目录是否随包存在。MSVC 构建还要考虑目标机器上的 Microsoft Visual C++ Runtime；MinGW 构建需匹配相应运行库。不要把开发机整个 Qt 安装目录直接打包，也不要用不同编译器套件的 windeployqt。

macOS

Qt 提供 macdeployqt 将 Qt 库和插件收集到 .app bundle。部署完成后再进行代码签名；如需分发给其他 Mac 用户，还要按分发方式处理公证与安装镜像。更改 bundle 内文件后通常需要重新签名。目标系统版本应不低于应用编译时设定的最低版本，CPU 架构要与目标用户设备匹配（或构建通用二进制）。

Linux

Linux 没有一个适用于所有发行版的万能部署器。常见方式包括 AppImage、发行版包、容器化交付或为目标发行版构建。除了 Qt 库，还需关注 glibc/系统库版本兼容、平台插件、字体、图像插件和系统主题依赖。不能在比目标系统更新很多的发行版上编译后，就假设旧系统也能运行。

运行时报 Could not find the Qt platform plugin "xcb" 等错误时，先用 QT_DEBUG_PLUGINS=1 查看插件搜索路径和加载失败原因；确保插件目录随程序发布，且其系统依赖齐全。不要把 QT_PLUGIN_PATH 永久设置成开发机路径。

打包前检查清单

  1. 用 Release 构建，并确认目标系统与 CPU 架构。
  2. 通过 CMake install/deploy API 或平台工具收集运行库和插件。
  3. 检查应用图标、翻译、配置模板、证书等非代码资源。
  4. 在没有安装 Qt SDK 的干净环境启动应用，试一遍常用功能。
  5. 检查启动日志、动态库依赖、文件读写权限和默认数据目录。
  6. 按目标平台的许可和第三方依赖要求准备随包 notices。

部署属于每个目标平台的构建流程；应在对应平台上产出和验证交付物，不要假设一个桌面二进制能跨操作系统复用。参考 Qt CMake Deployment、Windows Deployment 和 macOS Deployment。
